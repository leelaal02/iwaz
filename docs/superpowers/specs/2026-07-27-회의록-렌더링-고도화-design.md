# 회의록 docx 렌더링 고도화 — 설계 (Spec)

- 작성일: 2026-07-27
- 대상 스킬: `.claude/skills/meeting-minutes/`
- 브랜치: `feat/meeting-minutes-skill`

## 1. 배경 / 문제

STT→추출→양식 채움 파이프라인으로 세 양식(KISA·누리미디어·일반)에 회의록을 채웠으나, 사용자 피드백:

1. 원래 양식에 맞춰 내용이 **제대로** 들어가야 함(정합성).
2. Action Item의 **담당자·기한(Due Date)을 표의 각 컬럼에 자동 채움**. 미지정 시 "입력필요"(빨간 글씨).
3. 논의 **소제목이 눈에 안 띔** → 넘버링 + 굵게로 가독성 향상(중요).
4. **빈칸(값 슬롯)에 "입력필요"(빨간 굵은 글씨)** — Action Item 표뿐 아니라 **모든 표·모든 미지정 컬럼**에 일괄.

## 2. 확정 규칙 (사용자 합의)

- 적용 범위: **스킬 자체 개선**(향후 모든 회의록에 자동 적용) + 기존 3개 파일 재생성.
- "입력필요" 표기: **빨간(FF0000) 굵은 "입력필요"**.
- 소제목: **넘버링 + 굵게**("1. 컨설팅 …").
- **"입력필요"는 음성(→minutes.json)에 없는 내용에만.** 데이터가 있으면 그 값을 채우고 절대 "입력필요"로 덮지 않음.
- 음성엔 있으나 9항목 밖 내용 → `notes`(기타·특이사항) 캐치올로 보존(버리지 않음).
- 9항목 스키마는 **불변**(CLAUDE.md 제약). 양식 전용 라벨칸(장소·작성자·회의장소·첨부 등)은 9항목에 없으므로:
  - 원문에 해당 정보가 있으면 → `literal`(그 값) 채움.
  - 없으면 → `todo`("입력필요").

## 3. 메커니즘

docxtpl `RichText`(색·굵기) + jinja 넘버링을 **렌더 컨텍스트**에서 부여한다. 렌더 후 후처리는 최소화. 검증: docxtpl 0.20.2, jinja2 3.1.6, RichText 정상.

- **데이터 유무에 따라 서식이 갈리는 값**(빈 스칼라, action owner/due, 소제목) → `build_context`가 RichText로 생성.
- **정적 슬롯**(양식 전용 빈칸) → 매핑에서 `todo`/`literal` 지정 → 토큰/텍스트 삽입.

## 4. 변경 상세

### 4.1 `scripts/render_docx_template.py` — `build_context` 확장

```python
from docxtpl import RichText

def _todo():                       # 공통 "입력필요" 빨간 굵게
    rt = RichText(); rt.add("입력필요", color="FF0000", bold=True); return rt

def _scalar(v):                    # 값 있으면 문자열, 없으면 todo
    return v if (v not in (None, "", [])) else _todo()

def _numbered_bold(i, text):       # "N. text" 굵게
    rt = RichText(); rt.add(f"{i}. {text}", bold=True); return rt

def _label_bold(text):             # 섹션 라벨 굵게
    rt = RichText(); rt.add(text, bold=True); return rt
```

컨텍스트 추가/변경:
- `todo`: `_todo()` (매핑 `todo` 모드가 참조하는 `{{ todo }}`).
- 스칼라(`date`,`purpose`,`next_meeting`,`title`,`attendees_joined`): 빈 값이면 `_todo()`.
  - `attendees_joined`: 빈 배열이면 `_todo()`, 아니면 기존처럼 join.
- `discussion`: 각 항목에 `topic_rt = _numbered_bold(i, topic)` 필드 추가(원본 `topic`·`points` 유지). 번호 `i`는 1부터.
- `action_items`: `owner`/`due`가 null → `_todo()` (기존 `"-"` 대체).
- 섹션 라벨 RichText: `label_discussion`,`label_decisions`,`label_action_items`,`label_notes`,`label_purpose` 등 = `_label_bold(...)`.

> autoescape=True 유지. RichText는 XML로 직접 삽입되어 이스케이프 무관(값 문자열만 이스케이프됨).

### 4.2 `scripts/apply_form_mapping.py` — 모드/블록 확장

**새 모드 3종**
- `todo`: 대상 칸/문단에 `{{ todo }}` 토큰 삽입(라벨 있으면 뒤에 append, 빈칸이면 첫 문단에). fields 불필요.
- `literal`: 대상 칸/문단에 `text`(매핑에 명시한 문자열)를 그대로 삽입. fields 대신 `text` 키 사용. 원문에서 찾은 값 채움용.
- `table_rows`: 지정 표를 Action Item **컬럼 채움**으로 변환.
  - 매핑 예: `{"mode":"table_rows","table":1,"row":2,"cols":{"task":0,"owner":4,"due":3}}`
  - 동작: `row`(데이터 행)의 지정 컬럼에 `{{ a.task }}`/`{{ a.owner }}`/`{{ a.due }}` 삽입, 그 **앞 행**에 `{%tr for a in action_items %}`, **뒤 행**에 `{%tr endfor %}`를 새 `<w:tr>`로 끼움(lxml addprevious/addnext, 데이터 행 XML을 복제해 셀 비우고 태그만).
  - 렌더 시 docxtpl가 데이터 행을 항목 수만큼 반복. owner/due 없으면 컬럼에 "입력필요"(RichText).

**기존 블록 개선**
- `discussion` 블록: `[{{ d.topic }}]` → `{{ d.topic_rt }}` (번호·굵게).
- block 다중 필드의 섹션 라벨: 리터럴 `"[논의 내용]"` → `{{ label_discussion }}` 등 굵은 RichText 토큰.
- `_SECTION_LABEL`는 컨텍스트 라벨 키와 매핑되도록 유지/정리.

### 4.3 매핑 파일 갱신 (`output/.work/*` 및 스킬 예시)

원문 재확인 결과 장소·작성자·회의장소·첨부·다음회의는 음성에 없음 → 해당 슬롯은 `todo`.

- **KISA**: `장소:`(r3c0)·`소속/성명·직급:`(r3c1) → `todo`. 실행항목은 향후계획 블록(owner/due 없으면 "입력필요" 자동).
- **누리미디어**:
  - t0: 작성자(r0c3)·회의장소(r1c3) → `todo`.
  - t1: action_items → `table_rows`(task=c0, due=c3, owner=c4). 미결사항(r4c2)·다음회의(r6)·첨부(r7c1) → `todo`.
- **일반 양식**: `ㅇ (장소)`(para5) → `todo`.

### 4.4 산출물 위치 규칙 준수

중간 파일(`*_tokenized.docx`, 매핑)은 `output/.work/`, 최종 3종 docx만 `output/`.

## 5. 테스트 (`tests/`)

- `test_apply_form_mapping.py`: `todo`/`literal`/`table_rows` 모드가 올바른 토큰/구조를 생성.
- `test_render_docx_template.py`(신규 또는 확장): 빈 스칼라→"입력필요" 런(색 FF0000·bold), discussion topic이 "1. …" 굵게, action owner/due null→"입력필요", 채워진 값은 "입력필요" 없음.
- 회귀: 기존 토큰 양식(has_tokens) 경로 정상.

## 6. 리스크 / 주의

- `{%tr%}` 행 삽입: 새 `<w:tr>`는 데이터 행 XML 복제로 그리드 폭 유지. 태그 행은 렌더 시 삭제됨.
- RichText가 `inline` append(라벨 뒤)에서도 동작: `todo`는 토큰이라 render가 처리하므로 문제없음.
- 병합 셀 좌표는 원점(merged origin) 기준(기존과 동일).
- 넘버링은 discussion topic에만(결정/실행/기타는 불릿 유지, 섹션 라벨만 굵게).

## 7. 완료 기준 (Acceptance)

1. 세 양식 모두 데이터 있는 곳은 정확히 채워지고, 음성에 없는 값 슬롯은 전부 빨간 굵은 "입력필요".
2. 누리미디어 Action Item이 담당자·Due Date 컬럼으로 분리 채움, 기한 없으면 컬럼에 "입력필요".
3. 논의 소제목이 "1. …/2. …" 넘버링 + 굵게로 표시.
4. 채워진 값 위에 "입력필요"가 덮이지 않음.
5. `pytest` 통과.
